# Ch2 Section 4 — 边缘计算与车载BMS部署（完整中文版）

---

## 整体定位

Section 2 和 Section 3 讨论了"用什么方法"估计 SoH。本节回答下一个问题：模型训好后，**在哪里运行**？本节从边缘计算的视角分析车载 BMS 的计算架构选择，介绍目标硬件平台和 ML 模型编译部署的技术链路，并回顾已有的 MCU 部署工作。本节为 Ch3 的完整部署流程和 Ch4 的硬件性能测量提供了平台背景。

## 4.1 计算架构选择：云端 vs 边缘

BMS 的 SoH 估计是一个实时性要求高、安全影响大、且需要长期持续运行的计算任务。这一任务应该在什么地方执行？有两条基本路径。

### 4.1.1 云端推理及其代价

云端方案将模型推理放在远程服务器上：车辆通过车载通信模块（TCU）将电池数据上传至云端，云端运行模型并将推理结果返回车辆。

**优势**显然：云端服务器几乎没有算力限制。可以使用任意大小的深度学习模型，可以利用全车队的聚合数据进行模型更新，可以灵活调整算法。

**代价**也同样显著：

- **延迟**：4G/5G 蜂窝网络的往返延迟通常在 30–100 ms 以上。对导航和音乐播放这不是问题；对 SoH 估计本身也不算紧急。但 SoH 和 SoC 的推理结果会被下游的充放电控制、热管理和故障检测模块消费——如果这些模块依赖的 SoH 估计值延迟到达，与之耦合的保护逻辑的响应速度也会受到连累。在最极端的情况下（如检测到电池异常发热），毫秒级的判断延迟可能导致完全不同的安全后果

- **带宽**：一块典型 EV 电池包包含数十到上百个电芯。每个电芯的电压和温度以 1–10 Hz 频率采样，加上电流和系统级数据，一个 BMS 每秒可产生数 KB 到数十 KB 的原始数据。如果全部上传，单车每日的数据量可达数百 MB。乘以车队规模，这是一笔持续的通信成本

- **网络不可用**：地下停车场、隧道、山区和偏远道路上蜂窝信号可能消失。依靠云端推理的系统在这些场景下退化为无监控状态——恰好是电池安全风险较高的场景（地下充电、山区上坡大电流放电）

- **数据隐私与法规**：电池运行数据反映了车辆的使用模式、充电地点和时间、驾驶风格等信息。将这些数据持续上传到第三方云端引发隐私和合规风险，尤其在欧盟 GDPR 等严格法规框架下

### 4.1.2 边缘推理的理由

边缘方案将推理放在车载 BMS 处理器上本地执行。数据从传感器采集后，不离开 ECU，直接在本地完成特征提取和模型推理。结果以微秒级延迟交付给下游控制逻辑。

边缘推理为 BMS 场景提供的核心价值：

- **延迟消失**：推理在本地完成，不经过任何网络跳。从传感器采样到 SoH 估计值更新，整个周期的延迟取决于 MCU 的处理速度——在本文的目标硬件上约 0.4 ms

- **离线可用**：不依赖外部网络，车辆在任何位置、任何通信条件下都保持完全的 BMS 功能

- **数据本地化**：电池运行数据不出车，隐私风险为零

- **可预测性**：车载 MCU 提供确定性的任务调度。推理延迟不是"平均 0.4 ms"而是"最坏情况下 0.4 ms"——对实时系统而言，确定性比平均性能更重要

**代价**：MCU 资源极度受限（下节详述），模型必须经过专门的编译优化才可能运行。

### 4.1.3 云边协同——本论文的架构选择

纯云端和纯边缘代表了两个极端。本论文采用的是云边协同架构：

- **边缘负责实时推理**：SoH 模型在车载 MCU 上运行，满足低延迟、离线可用和隐私要求
- **云端负责训练和重训练**：初始模型在云端服务器上训练（不受资源约束）；长期运行中，云端聚合车辆累积数据并重训练模型

云边之间的连接通道是 OTA 更新（Section 6）。这一架构将实时性需求（边缘处理）和规模性需求（云端训练）分离开来，各取所长。

## 4.2 汽车 MCU 平台：SPC58EC80E5

### 4.2.1 汽车 MCU 与通用 MCU 的区别

汽车级微控制器与通用嵌入式处理器有几个根本区别：

- **温度范围**：必须保证在 -40°C 到 +125°C 的整个发动机舱温度范围内可靠运行。消费级芯片的工作温度上限通常为 85°C
- **功能安全**：必须符合 ISO 26262 标准，关键模块（CPU 核、内存、通信总线）具备硬件冗余、ECC 纠错、故障注入检测等安全机制
- **长供货周期**：汽车产品生命周期长达 10–15 年，芯片供应商须保证在此期间持续供货
- **电磁兼容性**：必须在发动机点火、电机驱动等强电磁干扰环境下正常工作

这些要求使汽车 MCU 的单核性能通常落后于同期消费级嵌入式芯片——安全机制和可靠性设计消耗了可观的芯片面积和功耗预算。

### 4.2.2 SPC58EC80E5 规格

本论文的部署实验在 STMicroelectronics 的 SPC58EC80E5 微控制器上进行。该芯片属于 SPC58 系列，定位为汽车车身和动力总成应用：

- **CPU**：双核 Power Architecture e200z420n3，主频 120 MHz。双核支持锁步（lockstep）模式——两个核执行相同的指令流，硬件比较结果，若不一致则触发故障。这满足 ASIL-D 的功能安全要求。本论文的部署使用单核模式以最大化算力

- **存储**：4 MB 片内 Flash（用于代码和只读数据如模型参数）、608 KB 片内 SRAM（用于运行时数据和栈）。没有外部 DRAM。所有软件必须在这 608 KB RAM 内运行

- **外设**：CAN FD、LIN、Ethernet、FlexRay 等汽车通信接口。本论文不直接使用这些外设——模型推理在 CPU 上完成，推理结果通过串口输出到 PC 进行记录

- **开发工具链**：使用 **SPC5Studio IDE** 进行代码编译和烧录——SPC5Studio 基于 Eclipse，集成 GCC Power Architecture 交叉编译器、SPC5 硬件抽象层以及 Flash 编程工具。程序的运行和调试使用 **UDE Starterkit**（Universal Debug Engine，PLS 公司），提供断点、单步执行、内存查看和变量监控等功能。性能分析数据（执行周期计数、Flash/RAM 占用）通过 SPC5Studio 的链接器输出（map 文件）和 UDE 的周期计数器获取

### 4.2.3 硬件平台的全貌

SPC58EC80E5 是 ST 官方 BMS 评估套件的核心计算单元。该套件还包括：

- **电气隔离单元**：在高压电池包（数百伏）和低压 MCU（3.3V/5V）之间提供电气隔离，通过变压器或电容耦合实现数字信号的跨隔离传输
- **电池模拟前端（AFE）**：执行多电芯电压的精确采集（典型精度 ±1–5 mV）和温度测量。AFE 与 MCU 通过 SPI 或专用通信协议交换数据
- **电池盒**：容纳实际的锂离子电池单体，提供电芯连接、平衡电路和温度传感器接口

作者搭建了该套件的完整硬件环境并完成了配置说明书的研读和各组件之间的通信配置。本论文的模型部署在 SPC58 单板上进行：通过串口向 MCU 发送预存的测试数据（模拟传感器输入），MCU 在本地完成特征提取和模型推理，再将结果通过串口返回 PC 进行记录和分析。这一方式验证了模型在 MCU 上的实时推理能力，同时避免了 AFE 和电池盒引入的物理变量对基准测试的影响。

## 4.3 ML 模型到 MCU 的编译链路

将一个在 Python 中训练好的 ML 模型放到 MCU 上运行，需要经过一次"翻译"——将模型结构从 Python 对象转换为 MCU 可以执行的 C 代码。这期间有几个关键约束：

- **无动态内存分配**：车载 BMS 固件通常禁止 malloc/free（可能导致内存碎片和分配失败）。所有数据结构必须在编译时确定尺寸
- **无外部依赖**：生成的代码必须是自包含的——不能在运行时依赖 Python 解释器、NumPy 或任何 ML 框架
- **无系统调用**：MCU 通常运行裸机固件或轻量 RTOS，没有 Linux 式的文件系统和进程管理

### 4.3.1 面向神经网络的工具

部署神经网络到 MCU 的主流选择包括：

- **TensorFlow Lite for Microcontrollers**：提供精简的 C++ 运行时，支持量化后的神经网络推理。对 Cortex-M 系列 MCU 支持较好，但对 Power Architecture（如 SPC58）没有官方支持

- **STM X-CUBE-AI**：ST 官方的工具链扩展，将 Keras/TensorFlow 模型自动转换为 STM32 的优化 C 代码。然而该工具主要面向 ARM Cortex-M 架构的 STM32 系列，不支持 SPC58 的 Power Architecture

这两个工具的共同局限是**仅支持神经网络架构**，不能转换决策树或树集成模型。

### 4.3.2 EDEN 编译器——面向决策树集合

EDEN（Efficient Decision tree Ensembles）编译器是一个开源的、面向 IoT 边缘节点的决策树集合编译器。最初设计用于随机森林，在本论文中由合作者扩展以支持 LightGBM 的梯度提升树格式。

**编译过程**：EDEN 将 LightGBM 训练得到的每棵决策树转换为一个紧凑的数组表示：

- **分裂阈值数组**：对树中的每个节点（内部节点或叶节点），存储其分裂阈值。若为叶节点，存储该叶的预测值
- **特征索引数组**：对每个节点，存储用于分裂的特征编号（0–9，对应 10 个特征）。若为叶节点，该字段值设为 NUM_FEATURES + 1，作为叶节点的标志位
- **右子节点索引数组**：树节点在数组中按前序遍历顺序排列。因此，任何节点的左子节点隐式地是其下一个数组元素，只需显式存储右子节点的索引。这比完整存储左右子树各节省一个索引数组
- **树根索引数组**：记录集成中每棵树的根节点在节点数组中的起始位置，用于遍历所有树的循环

**推理过程**：对每棵树，从根节点开始：
1. 读取特征索引数组[x] → 获取特征 j
2. 从输入特征向量 f 中取 f[j]，与阈值数组[x]比较
3. 若 f[j] ≤ threshold[x]，移动到 x+1（左子节点）；否则移动到 right_child[x]
4. 若特征索引标记为叶节点（> NUM_FEATURES），则累加阈值数组[x]中的预测值，结束此树遍历
5. 重复直到所有树遍历完毕，累积结果即为 SoH 预测值

**关键特性**：
- 生成的 C 代码约为一个 .c 文件，包含数组定义和推理函数，可直接加入固件工程
- 无任何外部依赖，仅需标准 C 库（memcpy、基本数学函数）
- 所有数组在编译时确定尺寸和内容（const 声明），存储在 Flash 中
- 推理不使用动态内存，仅需 ~100 字节栈空间用于临时变量

## 4.4 已有 MCU 部署工作：BiLSTM 基线

Sammartino 等人将 BiLSTM 模型部署到 SPC58 MCU 的工作是少数完整的 SoH 估计"训练→部署"案例，也是本论文选为对比基线的直接原因。

**工作内容**：
- 训练了一个 BiLSTM 模型用于 NASA 电池数据集的 SoH 估计
- 通过 STM 的 X-CUBE-AI 工具链将 Keras 模型转换为 C 代码
- 部署到 SPC58 MCU 上运行，测量了推理延迟和内存占用

**贡献与局限**：
该工作验证了"深度模型上汽车 MCU"的技术可行性，但存在以下局限：

1. **固定窗口假设**：模型输入为固定 20 采样点的窗口。在实际部署中，若 BMS 的采样率或应用场景变化导致有效窗口长度改变，模型必须重新训练
2. **满电起始假设**：该工作假设每个放电周期从满电状态（SoC=100%）开始。真实驾驶中，绝大多数行程从中间 SoC 开始，且放电过程常被中断
3. **数据分割**：训练集、验证集和测试集来自相同电池单体，不能评估模型跨单体的泛化能力——而实际 BMS 必须在不同电池之间（甚至不同批次、不同化学体系之间）保持稳定性

本论文的工作在与该基线相同硬件平台上进行，采用完全相同的数据分割和评估协议，确保了对比的公平性。第4章的实验结果将展示 LightGBM 在多个维度上对该基线的超越。

## 本节小结（过渡到 Section 5）

本节讨论了将 SoH 估计模型部署到车载硬件的计算架构选择和技术链路。云边协同架构是目前最务实的方案——边缘处理实时推理，云端负责训练和更新。SPC58EC80E5 是本论文的目标 MCU，通过 EDEN 编译的 LightGBM 模型可在其上高效运行。Sammartino 等人的 BiLSTM 部署工作提供了一个直接、公平的对比基线。

从本节的技术讨论中产生一个自然的问题：模型部署到车上之后，接下来怎么办？电池在老化，车在跑，数据在累积——仅部署一个静态模型是不够的，需要一个长期的维护和更新策略。这引出了 Digital Twin 概念，即 Section 5 的主题。
